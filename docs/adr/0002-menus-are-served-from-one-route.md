# Menus are served from one route, worked out from routes and declarations

8.1.0 rendered an endpoint's menu when a request added `?menu`, by running the action and reading what it passed to `surrender`. That made the menu exact, but a client had to ask every endpoint separately, a member route needed the id of a record that exists, and a reserved query param could hide one of the app's own. 8.2.0 serves every endpoint's menu from one route, `GET /surrender_menu`, which can't run actions, so it works out each endpoint from the route and the controller instead: the model from the controller's name, and a collection from the action and whether its path has an `:id`. What it can't infer, a controller declares with `surrender_options`, and `surrender` applies the same declaration, so a declared include, exclude or pagination can't drift from the menu. We considered requiring a declaration for every action, which is never wrong but repeats each action's call to `surrender`, and inferring only, which needs no new API but can't see a controller's include, exclude or pagination at all. As a consequence, what an action decides as it runs (`surrender`'s own `include:` and `exclude:`, and `skip_pagination`) doesn't reach the menu, the menu lists a model's fields rather than an STI subclass's, and it is visible to anyone who can reach its path, since the app's authentication doesn't apply to surrender's controller.
